# CLAUDE.md — Book CRUD API

## Mission

Build a maintainable, production-minded, Dockerized CRUD REST API for managing books. Teach and demonstrate:

- Clean Architecture and separation of concerns
- SOLID principles
- Java 21 and Spring Boot
- JPA, Hibernate, Spring Data JPA, entity lifecycle and persistence context
- Microsoft SQL Server and stored procedures
- Validation, error handling, API documentation, tests, configuration, and Docker

Do not generate a toy implementation that ignores the architecture or database requirements.

## Technology baseline

- Java 21
- Maven
- Spring Boot 3.x, with a mutually compatible stable patch
- Spring Web
- Spring Validation
- Spring Data JPA / Hibernate
- Microsoft SQL Server, not PostgreSQL
- Flyway migrations
- Springdoc OpenAPI / Swagger UI
- JUnit 5 and Spring Boot Test
- Testcontainers for SQL Server integration tests when the environment supports Docker
- Docker and Docker Compose

Use Spring Boot's dependency management. Do not independently pin Hibernate, Spring Framework, or Jakarta Persistence versions unless there is a verified compatibility reason. Use `jakarta.persistence.*`, not legacy `javax.persistence.*`.

## Database assumption

Use Microsoft SQL Server. Stored procedures are required. Use SQL Server-compatible SQL and T-SQL syntax. Never use PostgreSQL-only syntax, `REFCURSOR`, `SERIAL`, `ON CONFLICT`, or PostgreSQL drivers.

The database is authoritative for schema and stored-procedure definitions. Flyway owns schema/procedure deployment. Configure Hibernate with `spring.jpa.hibernate.ddl-auto=validate`; never use `create`, `create-drop`, or `update`.

## Book data model

Book fields:

- `id`: unique primary key, generated by the database using `BIGINT IDENTITY(1,1)` unless a reason is documented
- `title`: required string, trimmed, sensible max length
- `description`: optional string
- `stock`: enum with exactly `AVAILABLE`, `BOOKED`, `OUT_OF_STOCK`
- `isShown`: boolean
- `price`: decimal value using `BigDecimal`, never `double`/`float` for money
- `createdAt` and `updatedAt`: recommended audit timestamps; add them only if implemented consistently and documented

API values for stock should be stable and explicit, for example `AVAILABLE`, `BOOKED`, and `OUT_OF_STOCK`. Document the mapping between Java enum constants and SQL Server storage. Prefer storing the enum as a string (`EnumType.STRING`) if Hibernate directly persists it. If stored procedures use explicit string values, validate and convert them consistently. Never persist ordinal enum values.

Do not confuse stock status with a numeric stock quantity. The requested model contains a status enum, not a quantity. Do not add quantity unless explicitly approved.

## Required application behavior

Implement CRUD endpoints, with appropriate HTTP status codes:

- `POST /api/books` — create a book
- `GET /api/books/{id}` — get one book
- `GET /api/books` — list books, with pagination and sorting if reasonable
- `PUT /api/books/{id}` — update a book
- `DELETE /api/books/{id}` — delete a book
- Optional `GET /api/books?isShown=true&stock=AVAILABLE` filters only if implemented cleanly and documented

Use DTOs for requests and responses. Never expose JPA entities directly from controllers. Validate input using Jakarta Bean Validation. Return consistent error responses using `@ControllerAdvice` / `ProblemDetail` or an equivalent documented structure. Return 404 when a book does not exist, 400 for invalid input, and appropriate conflict responses for duplicate or constraint violations.

## Stored procedure requirement

Implement and document SQL Server stored procedures for CRUD operations, for example:

- `dbo.Book_Create`
- `dbo.Book_GetById`
- `dbo.Book_GetAll` (support paging if implemented)
- `dbo.Book_Update`
- `dbo.Book_Delete`

Procedure names can be adjusted to match a consistent naming standard. All procedures must use parameters, not string-concatenated SQL. Return result sets or explicit output parameters consistently. Define how missing IDs and constraint failures are surfaced to the service layer.

Call stored procedures through a deliberate persistence adapter. Prefer `EntityManager`/JPA stored-procedure APIs where their result mapping is clear. Use `JdbcTemplate` or another Spring-managed JDBC mechanism when it is the more reliable option for SQL Server result sets or output parameters. Document why each approach is selected.

**Do not claim that `JpaRepository.save()` invokes a stored procedure automatically.** It does not unless explicitly configured. If CRUD is required to use procedures, route those operations through the procedure adapter. Spring Data JPA should still be used to teach ORM concepts and repository abstractions where appropriate, but avoid a misleading duplicate persistence path that bypasses the required procedures. If both JPA-generated CRUD and procedure-based CRUD are demonstrated, clearly separate them (e.g. a learning/demo profile) and explain which path is active.

Keep JPA entities mapped to the real schema, but do not assume a stored procedure result set automatically becomes a managed entity. Use explicit result mapping and refresh/clear the persistence context when necessary to avoid stale entity state. Avoid mapping a procedure's result to a managed entity unless column aliases and entity mapping fully match.

## Architecture and package structure

Use traditional Spring Boot layered architecture:

```
BookController → BookService → BookRepository → SQL Server
```

Package structure under `com.bookCRUD.backend`:

```text
  BackendApplication.java
  controller/
    BookController.java
  service/
    BookService.java
  repository/
    BookRepository.java          ← JdbcTemplate, calls stored procedures
  entity/
    BookEntity.java              ← JPA @Entity for ddl-auto=validate
    StockStatus.java
  dto/
    CreateBookRequest.java
    UpdateBookRequest.java
    BookResponse.java
  exception/
    BookNotFoundException.java
    ApiExceptionHandler.java
  config/                        ← OpenAPI/other config beans if needed
```

Keep controllers thin (HTTP only). Keep business logic in the service. Keep SQL in the repository. Do not put stored-procedure calls in the service layer.

Do not duplicate DTOs in multiple packages. Pick one clear location and use it consistently. Keep controller methods thin. Keep business rules out of entities and SQL-only mapping code out of the domain.

## Database requirements

- Use appropriate constraints, data types, and indexes.

## Migration requirements

- Use Flyway versioned migrations as the authoritative mechanism for database schema and stored-procedure deployment.
- Ensure Flyway runs against the SQL Server database during application startup.
- Configure Hibernate with `spring.jpa.hibernate.ddl-auto=validate`.
- Never rely on Hibernate to create, update, or drop database tables.
- Never modify an already-applied migration to introduce a new change; create a new migration.
- Avoid duplicate, conflicting SQL definitions between reference scripts and migration files. Document how reference scripts stay synchronized with migrations.
- Use SQL Server-compatible syntax, parameter types, procedure result sets, and error handling.

## Application integration

- Call the stored procedures through a dedicated persistence adapter.
- Use Spring Data JPA and Hibernate for genuine ORM learning and entity mapping.
- Do not assume that `JpaRepository.save()` automatically invokes a stored procedure.
- Use the same configured SQL Server DataSource and appropriate Spring-managed transaction boundaries for JPA and JDBC operations.
- Add integration tests that verify Flyway migrations and stored procedures against SQL Server.

## SOLID principles

Demonstrate them in actual code, not just comments:

- SRP: controller handles HTTP; service handles business logic and transactions; repository handles SQL/stored-procedure calls.
- OCP: add new endpoints or operations without rewriting existing ones.
- LSP: exceptions thrown by the repository honor the contract the service expects.
- ISP: keep repositories and services focused — do not add unrelated methods.
- DIP: controller depends on BookService (Spring-injected); service depends on BookRepository (Spring-injected). Constructor injection throughout.

## ORM and Hibernate learning requirements

Add documentation that explains:

- JPA specification vs Hibernate implementation vs Spring Data JPA abstraction
- entity vs domain model vs DTO
- transient, managed, detached, and removed entity states
- persistence context and first-level cache
- dirty checking and flush vs commit
- owning side and relationship mapping (only add relationships if the data model needs them)
- `EnumType.STRING`
- lazy/eager fetching and N+1 avoidance
- transaction boundaries and rollback
- why stored-procedure results and JPA-managed entities need careful synchronization
- why `ddl-auto=validate` and Flyway are used

Enable SQL logging only through a configurable profile/property. Do not log credentials or sensitive data. Do not use `spring.jpa.open-in-view=true`.

## Transactions

- Put transaction boundaries on application service/use-case methods or clearly documented application adapters.
- Ensure procedure calls and any related ORM work participate in the intended Spring-managed transaction.
- Use one configured DataSource for JPA and JDBC procedure calls.
- Use `@Transactional(readOnly = true)` for read-only service operations where appropriate.
- Define rollback behavior for checked exceptions if checked exceptions are used.
- Do not perform external network calls inside database transactions.
- If stored procedures modify rows that may also be represented by managed JPA entities, flush before the procedure if required and clear/refresh afterward when necessary. Explain and test this.

## Database and migrations

- Use Flyway versioned migrations in `src/main/resources/db/migration`, such as `V1__create_books_table.sql` and `V2__create_book_procedures.sql`.
- SQL Server table must include primary key, required title, description, stock status, `is_shown`/`isShown` consistent naming, and `DECIMAL(12,2)` price with a nonnegative constraint if appropriate.
- Add indexes only when justified by access patterns.
- Use `NVARCHAR` for user-facing text.
- Store booleans as `BIT`.
- Store stock status using a string column with a check constraint for allowed values.
- Keep procedures parameterized and deterministic. Use `SET NOCOUNT ON;` where appropriate.
- Define whether missing records return no rows, an output status, or a SQL error. Keep behavior consistent.
- Never edit an already-applied migration during ordinary development; add a new migration instead.
- Avoid destructive schema changes and never let Hibernate auto-update the schema.

## Security and configuration

- Externalize database credentials via environment variables. Provide `.env.example` with placeholders only; do not commit real `.env` files or secrets.
- Do not hardcode passwords, tokens, or connection strings containing secrets.
- Use a non-admin SQL Server login for the application where feasible; database initialization may require separate privileges.
- Document local development defaults and how to override them.
- This is a CRUD learning app. Do not add JWT/authentication unless requested; if no auth is implemented, document that it is not intended for public deployment as-is.
- Add basic CORS only if needed; do not use permissive wildcard configuration without a reason.

## Docker

## API docs

Configure Springdoc OpenAPI and document endpoints, schemas, validation failures, and stock enum values. Add Swagger UI access instructions to README. Ensure API docs reflect DTOs, not persistence entities.
